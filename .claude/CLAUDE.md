# Todo — working notes

A personal todo list with an Eisenhower matrix. A web client with no backend of its own: everything lives in the browser. Targets desktop and phone (iPhone, Android), installs as a PWA, works offline, and syncs between devices through the user's own [`workspace-server`](https://github.com/FLighter7/workspace-server) on the local network — paired once per device by a scanned or pasted code, then syncing on its own whenever the app is on screen, through the main server or, while it is out of reach, a server linked to it (a laptop's).

Stack: Vite 8 (Rolldown), Vue 3.5, TypeScript, Pinia 4, vue-router 5, Vuetify 4.1, vue-i18n 11, Vitest 4, SCSS modules, `idb`, `flag-icons`. Package manager: pnpm 10 (pinned in `packageManager`); never npm.

Every file in the repository is written in English — code, comments, docs, commit messages. The only exception is the localization files under `src/i18n/locales/`. Chat with the user happens in their language, which is Russian.

## Conventions

## Architecture

Full reference — folder tree, dependency direction, components-vs-containers, services-vs-repositories, naming — lives in [.claude/Architecture.md](Architecture.md). Read it before restructuring anything.

The short version: `pages → containers/components → stores → services/repositories → types`. **`services`/`repositories` know nothing about Vue or Pinia** — that is what keeps their tests free of a browser environment and the storage swappable. `ItemStorage` ([src/repositories/ItemStorage.ts](../src/repositories/ItemStorage.ts)) is the key boundary: `getAll / put / remove / clear / replaceAll`. The store does not know IndexedDB sits underneath; tests substitute `ItemMemoryRepository`.

The pages are **views of one collection**: `useItemsStore()` ([src/stores/items.ts](../src/stores/items.ts)) holds every item, and `tasks`, `groups`, `goals`, `dreams` are filters by `type`. The Eisenhower matrix is one more view: the store's `quadrants` getter splits the open tasks by `important` × `urgent` into `do / schedule / delegate / eliminate`.

## Data model

Every record is an **item** in one collection — one array in the store, one IndexedDB object store, one list in a backup or a sync payload — told apart by `type: ItemType`. `ItemType` is a numeric enum, `Task = 1 | Group = 2 | Goal = 3 | Dream = 4`, and it is **append-only**: those numbers are on disk, in backups and on the wire, so a value is never renumbered or reused. All items share an `ItemBase`: `id`, `type`, `name`, `note?`, `created`, `updated`, `status`. `Task` adds `important`, `urgent`, `schedule?`, `completions?`; `Dream`, `Goal` and `Group` add `color?` and `paintItems?`, the colour of the list section each heads (`SectionColor` in [src/types/color.ts](../src/types/color.ts)); `Goal` also adds `deadline?`. A group is deliberately a name and a colour: its dialog offers no note, and its builder sets none. `Item` is the union, tied to its drafts and parsers in [src/types/itemUnion.ts](../src/types/itemUnion.ts).

Links stay explicit fields rather than a generic parent: `Goal.dreamId`, `Task.goalId` and `Task.groupId`, all genuinely optional — a goal or a task can stand on its own with no parent, and a task can sit in a goal and a group at once. The tasks page still sections by goal only; a task's group shows in its own dialog.

`Status` is a real enum shared by every type: `Opened | Done | Cancelled`.

A separate document, `AppSettings`, lives beside the items but is not itself one: `general: {theme, scheme, accent, locale, startPage, cleanupDays, fontScale, pages}` plus per-page `dreams/goals/groups/tasks: {rows, confirmDone, confirmReopen, sortOrder}`. The groups section keeps `rows` for a uniform shape, but the Settings page offers no rows toggle for it, since a group has no note to show on a second row; and `parseSettings` defaults a missing `groups` section, which every document saved before the Groups page lacks. `general.pages` says which of the five pages are shown, and all five may be off: then the bottom bar holds the add button alone, and Tasks is the one page that can still be opened — the start page, which nothing leads away from. A hidden page is gone from the whole interface (bottom bar, start page choices, its address, the add dialog's tab, its picker in other dialogs, its sections on other pages; the task tab goes once neither Tasks nor the matrix is shown), but no record changes: a task keeps the goal it sits in through an edit, and the cascade on cancel still follows the links. `isPageHidden` holds that exception, so the router guard, the start page choices and the add dialog all follow it, while the bottom bar reads the flags themselves. `keepStartPageShown` hands a hidden start page to the first page still shown, in the order Tasks, matrix, Goals, Dreams, Groups, and runs in `parseSettings` for any document and in `setPageVisible`, so the start page is never one the app refuses to show. A missing `pages`, or a missing key in it, shows that page. It persists to `localStorage['todo.settings']` via `SettingsService` (see Traps), not IndexedDB, and is wrapped in `useSettingsStore()`. It rides along in backup/restore (`Backup.settings?`, optional so a backup without one still validates), and a restore replaces all of it. **Settings are not synced** (the user's decision, 2026-11-07, to be revisited): each device keeps its own, and the document on the server carries no `settings`. The QR sync's Accept/Decline exchange went with it; the options for later are in [docs/decisions.md](../docs/decisions.md#settings).

Several things are easy to break without knowing them:

- **`updated` moves on every user change** — sync merges on it, and the later version wins — and **never** on garbage collection. A device that moved it on startup would win the next merge for free, just for having started.
- **There is no `deleted` flag.** A closed record (`Done` or `Cancelled`) is its own tombstone. Physical deletion happens only in `collectGarbage`, only once the record is older than the cleanup window — closing a record is the only deletion action the interface offers directly. `cleanupDays` (30/60/90, set in Settings) is user-editable, and shortening it does make more records eligible for the next `collectGarbage` sweep — but that sweep only removes records that are already closed and already past the (new, shorter) window, never an open one, never on the spot. That's why shortening it ships with a hint under the selector and deliberately no confirmation dialog: nothing disappears at the moment of the click, only later, and only what closing had already marked for eventual removal.
- **`completions` merge per `occurrence`, not as a value.** Whole-record last-write-wins would silently drop a mark made on the other device: two devices out of contact, one marking the 7th and the other the 14th, would otherwise produce two records neither of which holds both.
- **The effective cleanup window is the larger of the two devices'.** Each device purges past its own `cleanupDays` independently; a closed record keeps surviving somewhere in the system until the more generous device also purges it. That needs no negotiation and no code — it falls out of both sides doing the same local thing.

The IndexedDB schema is at version 4: one object store, `items`, keyed by `id`, with no indexes — the whole collection is read into memory and filtered there. Upgrading to version 4 drops whatever stores an older version left (`todos`, or version 3's `dreams`/`goals`/`tasks`) instead of migrating them. The app opens one `ItemDbRepository`, so one connection; nothing pools or caches it. A new item type needs no schema change at all. Changing a record's shape in a way old rows cannot parse means raising `APP_DB_VERSION` in [src/repositories/AppDatabase.ts](../src/repositories/AppDatabase.ts) and writing a migration that backfills old records without granting them an undeservedly fresh `updated`. `AppSettings` sits outside this schema entirely — it has its own format guard, `parseSettings()`, instead of a version-numbered migration.

## Traps already paid for

**Anything new that writes data has to be exercised at least once in a real browser.** Unit tests do not catch this: the in-memory storage silently accepts Vue's reactive proxies while IndexedDB rejects them — structured clone throws. The symptom is data that renders correctly and vanishes on reload. Write only plain copies (`{ ...record }`) to storage.

**Chrome on this machine cannot verify the PWA.** Build 150.0.7871.189 has a broken Cache API: `caches.open(...).put(...)` fails with `InvalidAccessError: Entry already exists` even on a clean profile. Use Edge. The diagnostic snippet is in the [README](../README.md#testing-the-pwa-locally).

**Vuetify 4 has no MD2 typography classes.** `text-h6`, `text-body-2`, `text-caption`, `text-subtitle-*` match nothing and fail silently; use the MD3 names (`text-title-large`, `text-body-medium`, `text-body-small`, …). Those classes set their own `font-family` from `--v-font-body`/`--v-font-heading`, which [fonts.scss](../src/assets/fonts/fonts.scss) points at Manrope/Alegreya — unset, they fall back to Roboto.

**Vuetify theme names are `${scheme}-${mode}`** (`standard-light`, `contrast-dark`, …), never `light` or `dark`. Vuetify's own `light` and `dark` themes are still registered, unused, so a selector or a `theme` prop aimed at them silently gets Vuetify's default blue palette. Target `[class*='v-theme--']`, or read `theme.current.value.dark`. Every colour drawn comes from the palettes in [src/plugins/theme.ts](../src/plugins/theme.ts), which the contrast test holds to WCAG; a literal colour in a component escapes it.

**Text size scales the root font size, so size new styles in rem.** The setting writes one multiplier to `--app-font-scale` on `<html>`; a px font size will not follow it, and a px box around em-sized content (Vuetify's icons) overflows at 150%. Vuetify's own px exceptions — fields, field messages, counters, checkbox boxes — are patched in [font-scale.scss](../src/assets/styles/font-scale.scss), and fields deliberately never drop below 16px: iOS Safari zooms into any input with smaller text. The bottom bar's labels are the one deliberate exception: five pages and the add button leave a phone no room for them at 150%, so each label stops growing at `22cqi` of its own button, while the icons still scale. Check new screens at 87.5% and 150%.

**Vuetify's own strings** (pagination, "Items per page") are localized through Vuetify's locale system in [src/plugins/vuetify.ts](../src/plugins/vuetify.ts), not vue-i18n: the adapter would need the runtime message compiler that precompilation removes.

**pnpm installs strictly.** A module the build resolves has to be a direct dependency: `workbox-window` is one only because `vite-plugin-pwa`'s `virtual:pwa-register` imports it, which npm's flat `node_modules` used to satisfy by accident. `pnpm.onlyBuiltDependencies` in `package.json` lists the dependencies whose install scripts may run (`esbuild`, `@parcel/watcher`); a new dependency that needs its script goes there, or pnpm skips it with a warning.

**The service worker precache must contain no duplicates.** A URL listed twice fails the install with `Entry already exists`, and offline mode silently does not work at all. Hence `includeManifestIcons: false` and no `includeAssets` in [vite.config.ts](../vite.config.ts).

**`pnpm run dev` never has a service worker.** `registerSW()` no-ops under the dev server unless `devOptions.enabled` is set, which this project deliberately does not do — dev mode precaches Vite's unbundled, HMR-versioned module graph rather than anything resembling the production bundle, and only matches `/` in its `navigateFallback`, so it cannot predict real offline behaviour anyway. "Nothing is cached, the page dies when the dev server stops" during `pnpm run dev` is expected, not a regression. Verify offline behaviour only through `pnpm run build && pnpm run preview`.

**The IndexedDB connection must close on `versionchange`**, otherwise a second tab carrying a new schema version hangs.

**Sync only works within one network.** There are deliberately no ICE servers — that would be an internet dependency. The device reaches the server, and each of its fallback servers, at the hosts in its pairing: the server's `<uuid>.local` name first, then its LAN IPv4 addresses. The name has to be a UUID with A records only — WebKit ignores any other `.local` name, and libwebrtc prefers IPv6 when a name has both kinds of record while the server listens on IPv4 only — which is the server's job, not this app's. Guest Wi-Fi with client isolation will not pass it.

**The server's copy wins ties, and a device writes only what the server lacks.** `planServerMerge` ([src/services/server/planServerMerge.ts](../src/services/server/planServerMerge.ts)) passes the server's list **first** to `syncMerger.mergeItems`, so the server wins an `updated` tie and a completion `at` tie on every device alike; with one shared copy, a tie each device settled its own way would be written back and forth forever. And it decides whether to write on the merge **before** garbage collection and pruning: collecting alone never causes a write, or a 30-day device and a 90-day one would take turns removing and restoring the same closed records, live, through `changed` pushes. Swap either and two devices loop.

**Nested reactive values reach storage through the draft.** `toRaw()` unwraps a record but not its fields; a form-bound `schedule` or `deadline` arrives as a proxy, and structured clone rejects it. The items store's `toStorable()` walks every level, and every write — `add`, `update`/`close`/`reopen`, `replaceAll` — goes through it, for the in-memory copy as much as for storage. A later write of a plain copy can cover up an earlier one that failed, which is why [e2e/items-persistence.spec.ts](../e2e/items-persistence.spec.ts) checks IndexedDB after each write.

**The store's `records` is a `shallowRef`, replaced on every write and never changed in place.** Pushing into the array or editing a record's field directly reaches neither the screen nor storage. Every change goes through a store action.

**`update()` takes the item type: `update(ItemType.Task, id, patch)`.** `Omit` does not distribute over a union, so a patch typed against `Item` alone would allow only the shared fields, and a draft held in a variable would slip past the excess-property check anyway. The type argument lets the patch be checked against that type's fields. A mismatched type is a no-op, and `id`, `type` and `created` are restored after the patch at runtime. A record's `type` never changes through a patch: a future type change has to rebuild the record with the target type's builder.

**Schedules store wall-clock time, never UTC.** A floating `10:00` must stay 10:00 in another country, and a zone-anchored one must survive its own daylight-saving change; a stored UTC instant breaks both. `created`, `updated` and `Completion.at` stay UTC — they are moments, not appointments.

**Backup files of versions 1–3 are refused, not migrated.** Versions 1 and 2 carry a single `todos` list, version 3 separate `dreams`/`goals`/`tasks` lists whose records have no `type`. Version 4 carries one `items` list, and moving to it deliberately started clean. Sync moved to schema 4 for the same reason, and to 5 when dreams, goals and groups gained a colour. The document on the server is a backup version 4 file plus `syncSchema` (`SYNC_SCHEMA`, [src/services/sync/syncSchema.ts](../src/services/sync/syncSchema.ts)): a build that finds a higher one there neither merges nor writes it, and one that finds a lower one writes it back with its own. The backup stayed at version 4 through that: the colour is optional, so every version 4 file still reads.

**Ids share one key space across every type.** Two items with the same id collapse into one record in IndexedDB without a word, so `BackupService.parse` refuses a file that repeats one. Keep fixture ids distinct across types in tests.

**Settings persist to `localStorage`, not IndexedDB.** `SettingsService.load()` never returns the shared `DEFAULT_SETTINGS` object directly — it clones it first, so nothing accidentally mutates the default. `loadRaw()` returns `null` for both a missing key and corrupt JSON alike, and that ambiguity is load-bearing: `detectLocale()` calls `loadRaw()`, never `load()`, because first-run OS-locale detection has to see a real `null` to know it's a first run — `load()`'s fallback would mask that behind `DEFAULT_SETTINGS`'s hardcoded `'en'`.

**The server pairing lives in `localStorage['todo.server']`, never in a backup.** It holds this device's token; a backup file travels and must not carry it. The key is set in [src/stores/serverSync.ts](../src/stores/serverSync.ts), and the record's shape belongs to the package's `createPairingStore`: change neither, or every paired device has to pair again. Its additions so far are optional: `fallbacks` (2026-11-12), the main's subordinates as its `welcome` lists them, and `term` (2026-11-12), the family's term the paired server last named as the main; a record saved before simply lacks them. The sync engine (`SyncEngine` from `@flighter/wss-client`) stops for good (until the device pairs again) on `serverChanged`, `badToken`, `unknownApp`, `protocol`, a document from a newer build (`newerSchema`) or one that does not parse (`badDocument`), and on its own write guard (more than 10 writes a minute); it retries a lost connection, a `blocked` address (once a minute) and a server-side `internal` failure — any unknown error code reads as one — only while the app is visible, keeping the pairing, and closes the connection whenever the app is hidden.

**The mock-data content pools must stay out of vue-i18n's precompilation.** `vite.config.ts`'s `vueI18n({ include: [...] })` glob for the locale message catalogs has to stay non-recursive (`./src/i18n/locales/*.json`), never `**` — `src/i18n/locales/mockData/{en,ru,pl}.json` (consumed by `src/services/mockData/pools.ts`) are plain sample-content word pools, not vue-i18n message catalogs, and a recursive glob would silently precompile every pool string into vue-i18n's compiled-message AST format instead of leaving it a plain string, corrupting the mock-data generator's output with no compile-time signal — JSON-import typing doesn't catch it. Separately, the generator's GC-safety (a page reload right after generating must never silently drop what the user just saw, regardless of `cleanupDays`) is enforced by `withinLastDays` in `src/services/mockData/MockDataService.ts` re-validating every emitted timestamp/occurrence/exdate entry against the true `now` at generation time — not by an argument that the recurrence math is naturally bounded, which turned out to be a documentation trap of its own.

**`pnpm run test:sr` drives the real keyboard.** Guidepup presses Tab, Enter, Escape and Alt+Esc at the OS level for the length of the run, so whatever window has the focus gets them too — an editor or a terminal included, where an Escape interrupts what is running. Start it only with the machine left alone, and never alongside other work in the same session.

## Process

Rationale and durable conventions from finished build stages live in [docs/decisions.md](../docs/decisions.md) — read it before touching sync, recurrence, completions, deadlines, settings, theming, or PWA/offline behaviour, since it records tradeoffs and invariants that aren't obvious from the code alone.

Stages 1–5 are done and merged into `main`: core, list, matrix, PWA/offline, export-import, sync. Stage 6 — reworking the data model into dreams, goals and tasks — is on `main` too; work now happens directly on `main`. The data layer and UI cutover onto it are done, and so is the settings sub-project (theme, locale, start page, cleanup window, per-page list preferences, wired into backup), dedicated dream and goal pages, the tasks page rework (`/tasks` replaces `/list` with Active/History tabs, task-under-goal grouping, a `goalId` picker, and a single tabbed `AddEntityDialog`), deadline UI (`DeadlineField` in `GoalDialog`/`AddEntityDialog`), recurrence UI (`ScheduleField` in `TaskDialog`/`AddEntityDialog`, backed by the `src/utils/schedule.ts` adapter), and completion history (`TaskCompletions` in `TaskDialog`'s read view, backed by the `setOccurrenceDone`/`setOccurrenceSkipped` store actions). On top of that, the three collections were folded into the one `Item` collection described above; the reasoning, the 10 000-record load analysis and the follow-ups it surfaced are in [docs/decisions.md](../docs/decisions.md#single-item-collection). Of those, sync now sends payloads in pieces with no size cap, and parsing, deadline labels and sorting are cached; list virtualization is deliberately deferred. Groups have their page too — `/groups`, between Goals and the add button in the bottom bar — with a `Task.groupId` picker in the task dialogs, the cascade on cancel, and their own tab in Settings; see [docs/decisions.md](../docs/decisions.md#dreamgoalgrouptask-pages--dialogs). Every page can be switched off in Settings, down to the add button alone with Tasks as the one page left; see [docs/decisions.md](../docs/decisions.md#settings). Settings itself is tabbed — General, then one tab per page, each starting with that page's switch. Theming is done too: five colour schemes, each light and dark (high contrast held to AAA among them), and an accent picked from swatches or by hand and fitted into each palette; see [docs/decisions.md](../docs/decisions.md#theming). Sections are coloured the same way: a dream, goal or group picks a colour for the section it heads, and optionally for the rows inside it, fitted into each palette like the accent; see [docs/decisions.md](../docs/decisions.md#section-colours).

The app was audited against WCAG 2.2 AA on 2026-10-27 and the serious findings fixed: the report and its backlog are in [docs/accessibility-audit.md](../docs/accessibility-audit.md), the conventions it settled in [docs/decisions.md](../docs/decisions.md#accessibility).

Deployment is set up: the `deploy` job in [.github/workflows/ci.yml](../.github/workflows/ci.yml) publishes `dist/` to GitHub Pages via `actions/deploy-pages` on every push to `main`, after `test` passes. See [README.md#deployment](../README.md#deployment). It is broken until the client package is on npm (below): GitHub Pages still serves a build from 2026-10-28, from before server sync.

Server sync replaced the QR peer-to-peer sync on 2026-11-10. The transport and the engine (the pairing code, the client-built SDP answer, framing, the protocol client, the pairing record and `SyncEngine`) live in the npm package `@flighter/wss-client`, built in workspace-server's `client/` folder so other apps share them. This app keeps what is about its own document, in `src/services/server/`: the synced document (`syncDocument`), the merge plan (`planServerMerge`) and the adapter that hands both to the engine (`todoSyncAdapter`). Around them sit the `serverSync` store, which `DefaultLayout` starts once the items have loaded, and the Sync page's `ServerSyncPanel`. **The package is published to npm by the user, by hand.** To try a change in it, run `pnpm add link:../workspace-server/client` and check the app against the link; never commit the link, and move to the registry version only after the user has published it. The one exception stands now: the link is committed, with the user's consent (2026-11-10), because no version has been published yet. CI cannot install it, so `test` and `deploy` fail until the user publishes the first version, the release candidate `1.0.0-rc.1` (on npm's `next` tag), and this app moves to exactly `1.0.0-rc.1`; once the user's checks pass, the final `1.0.0` follows and this app moves to `^1.0.0`. Its rationale, the user's decisions, the spike's findings and the open points are in [docs/decisions.md](../docs/decisions.md#syncwebrtc-transport); the contract is the server's `docs/protocol.md`. `e2e/server-sync.spec.ts` builds the server from `../workspace-server` (or `WORKSPACE_SERVER_DIR`) with Go, or runs `WORKSPACE_SERVER_BIN` on a machine without Go. A paired device passes the server's code on to another (Sync → "Pair another device", `PairingRelay`): it shows the code again as a QR code, with Share and Copy, and never pairs with it or stores it; see [docs/decisions.md](../docs/decisions.md#syncwebrtc-transport).

**Sync works through subordinates (2026-11-12).** The user's laptop can run a workspace-server linked to the main one as its subordinate, which keeps the main's documents and admits the main's devices. This device still pairs only with the main (the laptop's own code is refused, `notMain`), keeps the subordinates the main's `welcome` lists as the pairing's `fallbacks`, and when the main is out of reach syncs through one of them with the same token; the engine connects to all at once and prefers the main (`MAIN_GRACE_MS`). The Sync page then names that server under the main's ("Through {name} while this server is out of reach", `serverSync.via`). Nothing in the merge changed: the server's copy still wins a tie, and the main's copy wins on the subordinate. [e2e/server-hub.spec.ts](../e2e/server-hub.spec.ts) runs a main and a laptop's server from `../workspace-server`; see [docs/decisions.md](../docs/decisions.md#syncwebrtc-transport). The laptop's server can also take the main's role over (planned, or forced while the PC is away): a fallback that answers as the main at the pairing's `term` or a higher one becomes the paired server, so the device follows the main with no new pairing (the package's doing, nothing in this app).
