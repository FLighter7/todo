# Decisions

Durable rationale and conventions carried forward from the build stages' design docs (`docs/superpowers/specs/`, now deleted — every stage they described has shipped). `.claude/CLAUDE.md` covers day-to-day conventions and the traps already paid for; this file is the _why_ behind choices that aren't obvious from reading the code alone. Read it before revisiting any of these areas.

## Data model rationale

`Status` is a numeric enum rather than a `const enum` — `isolatedModules` forbids the latter — and it also covers a dream being deliberately abandoned ("changed my mind"), not just fulfilled. A goal's fuzzy `deadline: {year?, month?, day?, season?}` follows validation rules that live in `utils/deadline.ts`, not the type: `day` requires `month`; `month`/`day` and `season` are mutually exclusive; an empty object is invalid; a missing `year` means "the nearest future occurrence" and is allowed to drift in meaning year to year, by design; season boundaries are meteorological, so winter deliberately spans the Dec–Feb year boundary.

`Task.schedule` is a miniature VEVENT. There's no stored `periodType` field — one-time vs. recurring is derived from `rrule` being absent or `COUNT=1`, specifically to avoid two fields encoding the same fact and drifting apart. Editing a recurring task's schedule mutates the same record rather than splitting the series (no iCalendar `THIS-AND-FUTURE`); past completions stay valid because they're keyed by occurrence date, and a single moved occurrence is expressed via `exdate`+`rdate` instead. `pruneCompletions` exists because a recurring task is always `Opened` and therefore never swept by the general `collectGarbage` rule — left unbounded, a daily task over 5 years accumulates ~1800 completion entries.

`ItemDbRepository.getAll` skips invalid records — a row whose `type` this version does not know included — and surfaces a count via `lastError` rather than failing outright: a single corrupt record shouldn't take the whole list down. The sync payload carries a schema version and refuses a mismatch outright (`src/services/sync/SyncConnection.ts:169`, "The other device runs a different version. Update it and retry."). List order is a per-page setting (`PageSettings.sortOrder`, one of `newest`/`oldest`/`az`/`za`, default `newest`), not fixed — see `src/utils/sortEntities.ts`. Dates sort by `updated`, not `created`: a section's position (Tasks-under-Goal, Goals-under-Dream) follows its newest child's `updated` in both date modes, so adding or editing a record inside a section lifts the whole section; in `az`/`za` a section instead sorts by its own label. Sections and loose records are interleaved into one order, not rendered as two separate blocks. The list layout calls these _sections_ (`ListSection`, `EntityListSection`, `EntityRow.kind`), never groups, so they don't read as the stored `Group` type.

## Single item collection

Dreams, goals and tasks started as three collections — three IndexedDB object stores, three Pinia stores, three lists in every backup and sync payload. They were folded into one collection of items told apart by `type`, because the cost of a new type sat almost entirely in that plumbing: a new object store, a schema bump, new payload and backup lists, a new store, and new branches in `SyncFlow`, `BackupActions`, `MockDataActions` and `DefaultLayout`. With one collection a new type is an enum member, an interface, a parser, a builder and its UI. Relations stop needing bridges too: a container finds any parent through `byId`, and the rule that the stores must not know about each other — which kept parent labels and cascade counting out of them — no longer has anything to protect. Old data was deliberately not carried over: the version 4 IndexedDB upgrade drops the version 3 stores, and version 3 backups and schema 3 sync peers are refused.

`ItemType` is numeric to match `Status`, and ordered `Task = 1, Group = 2, Goal = 3, Dream = 4`. Those numbers are stored, so the enum is append-only. `Group` went into the enum, with a parser and builder, before it had any UI, because the exhaustive `Record<ItemType, …>` tables (parsers, builders) are what makes a new type compile-checked, and keeping it out would have meant revisiting them in the groups stage anyway. Links stay explicit fields (`Goal.dreamId`, `Task.goalId`, `Task.groupId`) rather than one generic `parentId`: a task can belong to a goal and a group at the same time, which a single parent cannot express. `Task.groupId` arrived without raising `SYNC_SCHEMA` or `BACKUP_VERSION` only because version 4 of both had never been deployed when it did. **Any field added to a record from now on has to raise `SYNC_SCHEMA`:** an older device's parser would drop the unknown field, and its next edit of that record would win the merge without it.

There are no per-type facade stores, not even as a migration step. A per-type `replaceAll` cannot be reproduced honestly on top of one collection, and tests seeding three facades one after another would overwrite each other's seeds. `add(type, draft)` takes the type as its own argument rather than as a draft field, because `TaskDialog` emits the same `TaskDraft` for adding and for editing, and a `type` inside it would leak into update patches. `update(type, id, patch)` takes it for typing: `Omit` does not distribute over a union, so a patch typed against `Item` alone allows only the shared fields. A mismatched type is a no-op. `id`, `type` and `created` are restored after the patch at runtime, so changing a record's type will mean rebuilding it with the target type's builder, never patching it. `SyncMerger.mergeItems` merges completions only when the winner is a task, and reads each side's marks only from a side that is a task. The sync payload now resolves with the parsed records rather than the raw JSON, so fields the parsers don't know never reach storage.

`records` is a `shallowRef` holding plain copies and replaced on every write. Deep reactivity over the whole collection made one edit cost about 9 ms at 10 000 records against 0.14 ms this way, and plain copies also cut the in-memory record loose from the form that produced its draft. The views — per-type `all/active/closed`, `quadrants`, `goalsByDream`, `tasksByGoal`, `byId` — are plain computeds over it. An earlier lesson still applies whenever one Pinia store is composed from another: a plain `{ ...store }` spread copies each property's value out once and nothing behind it stays connected, scalars and arrays alike, so the composition has to go through `storeToRefs` (or, for a document like the settings, `reactive()` + `toRefs()`).

The collection was sized against 10 000 synthetic records (1 000 dreams, 2 000 goals, 7 000 tasks, 30% of the tasks scheduled), measured in Node on a desktop; a phone is typically 3–5× slower. Reading, filtering and collecting the whole array costs fractions of a millisecond to a few milliseconds, and folding the collections changed none of the totals. The real costs lay elsewhere. Three were fixed as follow-ups; the before → after figures come from one Vitest run on the same desktop:

- **Sync was capped at 200 KB in a single message**, about 530 records at ~374 bytes each, and fewer with Cyrillic, since the check counted UTF-16 code units rather than bytes. A payload now goes out in pieces with no cap of its own — see [Sync/WebRTC transport](#syncwebrtc-transport).
- **Parsing built an `Intl.DateTimeFormat` per zoned task and parsed every RRULE** just to validate them. Zones and rules proven valid are now remembered by their string, and an invalid one is still rechecked and reported every time: 147 → 2 ms for 7 000 tasks, 2 000 of them scheduled.
- **`formatDeadline` built a formatter per goal, and the sort comparator parsed both dates on every comparison.** `dateTimeFormat` in `src/utils/intl.ts` now shares one formatter per locale and options (132 → 10 ms for 2 000 goals; `schedule.ts` goes through it too), and `sortEntityRows` computes each record's key once (73 → 4 ms for 7 000 tasks).

One is **deliberately deferred, not planned for now** (decided 2026-10-24): **lists render every row**, each a `VListItem` with a `VCheckboxBtn` — tens of thousands of component instances at 10 000 records. No real list is anywhere near that size; virtualization or a "show more" is the fix if one ever gets there.

`replaceAll` was the one cost that came within this refactor's reach: it used to await one transaction per record, and now runs a single transaction, which also makes a restore or sync all-or-nothing.

## Sync merge base rule

`CLAUDE.md`'s "`completions` merge per-occurrence" is the _exception_, not the rule. The base rule is whole-record last-write-wins by `updated`: a concurrent edit to two different fields on two devices loses the earlier edit entirely. Per-field conflict resolution was judged disproportionate for a manually-synced personal list. When `updated` matches to the millisecond on both sides, the first list passed to `SyncMerger.merge` wins — arbitrary, but it has to be deterministic or two devices merging the same pair could diverge permanently. With the QR sync that was the local list. With server sync it is the **server's**: `planServerMerge` passes the server's copy first, so it wins an `updated` tie and a completion `at` tie on every device alike. Local-wins was fine for two devices merging once; with a shared copy, two tied devices would each write their own version back and overwrite each other forever.

**A device writes only what the server lacks.** `planServerMerge` decides whether to write on the merge **before** garbage collection and pruning, comparing it with the server's list record by record (sorted by id, each record serialized with its keys sorted). Collecting and pruning alone never cause a write. Without that, a device with a 30-day cleanup window and one with 90 days would take turns removing and restoring the same closed records, and with live `changed` pushes they would do it forever. With it, the server's copy keeps a closed record until a device writes for some other reason; that writer sweeps by its own window, and a device with a longer window restores the record once and stops — the effective window stays the larger one, as it was between two devices. As a last line of defence, `ServerSyncEngine` stops writing after 10 writes within a minute, until the app starts again. That rule holds across types as well: if one id held a goal on one side and a task on the other, the newer record wins whole, and the completions merge only ever runs for a task winner.

## Recurrence / rrule gotchas

The `tzid`→wall-clock conversion in `nextOccurrence` needs **two** `Intl.DateTimeFormat` `formatToParts` passes to stay correct across a DST transition — verified against an anchored `America/New_York` 09:00 schedule read from a `Europe/Warsaw` host, which came out an hour off for a whole month without the second pass. A related trap: feeding that same machinery a value that's _already_ in the schedule's wall-clock domain re-triggers the instant→wall-clock conversion and silently reinterprets it against the device's own OS timezone. The fix was factoring a shared core that takes an already-converted comparison point; `nextOccurrence` is a thin wrapper over it, and `listOccurrences`/the last-occurrence check call the core directly.

An `rrule` that fits no UI preset (multiple `BYMONTHDAY`, `BYSETPOS`, etc.) parses to `undefined` and surfaces as a read-only "Custom" option — a safety net for foreign or hand-edited data, since this app's own editor is currently the only writer of `rrule`. "After N occurrences" floors at 2 in the UI because `isPeriodic()` treats `COUNT=1` as _not_ periodic — allowing 1 would let the form silently build a rule that behaves like a one-time task through a different control. An "until" date is converted to 23:59 wall-clock so the picked day is always fully included regardless of the schedule's own start time. The occurrence window shown in `TaskDialog` (5 past, 5 future) is a fixed constant, not a setting. `rdate` is honored when reading a schedule but nothing in the app authors one yet — only `exdate` is ever written, via the skip action.

## Completion-history invariants

An occurrence never carries both an `exdate` entry and a `completions` entry at once — each store action (`setOccurrenceDone`/`setOccurrenceSkipped`) clears the other side before writing its own. Un-marking a completion still _writes_ `{done: false, at: now}` rather than deleting the entry — deleting it would let a stale `done: true` from another device win after sync with nothing left to outrank it, the same tombstone logic as the "no `deleted` flag" rule applied to a single occurrence. The automatic Opened↔Done transition on a bounded series' last occurrence never touches a `Cancelled` task and fires with no confirmation, unlike the manual close/reopen flow gated by `confirmDone`/`confirmReopen` — it's a side effect of a deliberate occurrence action, not a standalone status change. Stray `completions`/`exdate` entries orphaned by an edited `rrule` aren't deleted immediately; they just stop appearing in `listOccurrences` and age out through the existing pruning window, the same "invisible now, removed later" shape as a closed record.

## Deadlines

`formatDeadline` builds its working `Date` from a fixed placeholder year (2000, a leap year) whenever `deadline.year` is unset, so a bare "Feb 29" doesn't throw; the placeholder never leaks into the displayed string because the `year` format option is omitted, not because the value is special-cased.

**`resolveDeadline()` — the `{from, to}` date-range resolution that sorting and overdue-detection would need — was specified but never built.** No later stage picked it up. Goals with a deadline currently have no sort-by-deadline or overdue indicator; don't assume one exists without checking.

## Cross-cutting store gotcha: patches with `undefined` overwrite

The items store's `update()` (`src/stores/items.ts`) spreads the patch over the existing record, so a patch key that's _present_ with value `undefined` really does overwrite the stored field — it isn't treated as "leave this alone." Any dialog that hand-maintains a subset of a record as its editable draft has to include every editable field in that subset, or saving from the dialog silently erases whatever it omitted. This bug hit `GoalList`/`deadline` and, independently, `TaskList`/`schedule` before being generically retired: `TaskDialog` now takes a full `record: Task | null` prop instead of a hand-picked `initial: Partial<TaskDraft>`. Follow the full-record-prop pattern for any future dialog rather than reintroducing a partial draft type.

## Settings

`src/plugins/vuetify.ts`, `src/i18n/index.ts`, and `src/router/index.ts` call `settingsService` directly instead of `useSettingsStore()`, because they resolve their startup values at module-evaluation time, before `createPinia()` has run. The settings Pinia store itself is built with `reactive()` + `toRefs()`, not a plain object spread — a spread was found elsewhere in this codebase to freeze reactivity. Settings writes to `localStorage` skip `toStorable()`/`toRaw()` entirely: `JSON.stringify` reads a reactive proxy fine, and the structured-clone-rejects-proxies trap is specific to `IndexedDB.put`, not `localStorage`. `ThemeMenu`/`LocaleMenu` deliberately stayed in the app bar rather than moving into the Settings page when their storage moved there — a setting with an existing fast, one-tap UI doesn't relocate just because its persistence layer changed. `ThemeMenu` only stores the mode; applying it is `useAppTheme`'s, with the scheme and the accent.

The text size setting (`general.fontScale`, five steps from 87.5% to 150%, landing on whole pixels at a 16px base) scales the root font size through a single CSS variable, `--app-font-scale`, which `App.vue` writes on `<html>` during setup — before the first paint, so a saved size never flashes in at the default. It works because Vuetify 4 sets its whole type scale in rem and its icons in em, and because every Vuetify rule sits in a cascade layer, so the app's unlayered overrides in `src/assets/styles/font-scale.scss` win without `!important`. The base is `100%`, not `16px`, so a larger default text size chosen in the browser or OS still applies underneath. The few Vuetify rules that hardcode px for text (`.v-field` 16px, `.v-messages` and `.v-counter` 12px) are rewritten in rem in that file rather than through Vuetify's SASS variables, which would mean compiling all of Vuetify's SASS on every build for three rules. Fields never drop below 16px, because iOS Safari zooms the page into any input with smaller text. Where a px box holds scaling content — a checkbox's 28px compact box around its 1.5em icon, BottomNav's 64px stacked buttons in a 4rem row — the box grows or stretches to fit instead of letting the content spill. BottomNav's labels are the exception: six slots on a 360px screen leave each one about 50px, and "Матрица" or "Marzenia" at 150% need nearly 80, so a label's size is capped at `22cqi` of its own button (each button is an inline-size container) while its icon keeps scaling. A browser without container units drops the rule and keeps Vuetify's size. The accessibility audit measured the price: since the add button grows with the text and leaves each label less room, the labels get slightly smaller as the text size goes up (10.0 → 9.2px at 320px from 100% to 150%). That was accepted as it is on 2026-10-27 ([A11Y-24](accessibility-audit.md#accepted-limitation)); showing the label on the current page only, once all five no longer fit, was the alternative set aside. `fontScale` is device-local, like the colour scheme and the accent ([Theming](#theming)): what reads well on a phone and on a desktop differs. Settings are not synced at all now (the user's decision, 2026-11-07, to be revisited); when they were, accepting a sync peer's settings kept this device's own value, and a backup restore still replaces it. `parseSettings` defaults the field to 1 when absent — a document saved before it existed failing to parse would make `loadRaw()` return null and silently reset every other setting with it.

Every page can be switched off (`general.pages`): Dreams, Goals and Groups since 2026-10-24, Tasks and the matrix since 2026-10-26. All five may be off (the user's rule): the bottom bar then holds the add button alone, and Tasks is the one page left — the start page, the only one the guard lets through, with no way to another page but Settings. Its switch stays off all the same; `isPageHidden` makes the exception, not the stored flags. A hidden page is hidden everywhere, not only from the bottom bar: its address leads to the start page through a `router.beforeEach` guard, it leaves the start page choices and the add dialog's tabs, its picker leaves the other dialogs, and the page it would section — goals on the Tasks page, dreams on the Goals page — runs as one flat list. Tasks show on two pages, so the add dialog's task tab goes only when Tasks and the matrix are both hidden — never with every page off, when Tasks is open again; the add dialog then opens on the first tab left. The records are left as they are. A dialog with a hidden picker still seeds that field from the record and saves it back, so editing a task while Goals is off keeps the goal it sits in, and switching the page back on restores the whole picture. The cascade on cancel follows the data the same way: cancelling a dream while Goals is off still offers to cancel its goals. `keepStartPageShown` hands a hidden start page to the first page still shown in `APP_PAGES` order — Tasks, matrix, Goals, Dreams, Groups, the user's choice (2026-10-26) — and runs in `setPageVisible` and in `parseSettings`, for any document, whether from localStorage or a backup. The router reads `settingsService` for the guard, like the `/` redirect, and the store writes localStorage on every change, so the two agree. Unlike `fontScale`, the set of pages travelled with a sync Accept while settings were synced: it describes how the app is used, not what a screen can hold. A missing `pages` shows every page, and a missing key shows that page, the same default-when-absent rule as `fontScale`. Since `pages` is the first nested object in `general`, every copy of a settings document goes through `cloneSettings`; a shallow copy would share it, and a write through the store would then reach `DEFAULT_SETTINGS`.

The Settings page is as wide as the main pages and splits into six tabs — General, then Tasks, Matrix, Goals, Dreams, Groups (the user's order, 2026-10-27) — and always opens on General, which holds the text size, the start page, the cleanup window, backup and sample data. Each page's tab starts with its "Show this page" switch, so the matrix, which has no preferences of its own, has a tab for that switch alone; the page's list preferences follow it. A hidden page keeps its tab, since that is where it is switched back on, and its preferences stay in view but disabled (the user's choice), values kept. Whether they are disabled follows `isPageHidden`, not the stored flag: with every page off, Tasks is still open, so its own stay within reach. Six tabs do not fit a phone, so the tab bar scrolls; they drop Vuetify's 90px minimum the way the add dialog's do, so as many fit as their labels allow. Each page's icon lives once, in `PAGE_ICONS` in `src/router/index.ts`: the bottom bar and the start page choices both read it, and once disagreed.

**Settings are not synced** since server sync replaced the QR sync (the user's decision, 2026-11-07, to be revisited). The QR sync sent them on request and the receiving side chose Accept or Decline; that flow went with it, and nothing replaces it yet. Each device keeps its own, and a backup still carries them. The options on the table: synced automatically, the latest change winning, with the text size, colour scheme and accent staying device-local and a `settingsUpdated` timestamp kept beside the document; or two explicit buttons on the Sync page, "Send my settings to the server" and "Take the settings from the server". Either can add a `settings` field to the server's document later without breaking its format, since a backup version 4 file already allows one.

## Theming

Three settings decide how the app looks, each independent of the others: the mode (`general.theme`: system, light or dark), the colour scheme (`general.scheme`) and the accent (`general.accent`). Each of the five schemes — standard (the warm palette the app started with), neutral, cool, pure black and high contrast — has a light and a dark palette in `src/plugins/theme.ts`, and all ten are registered with Vuetify as `${scheme}-${mode}`. `useAppTheme` (`src/composables/useAppTheme.ts`, called once from `App.vue`) shows the one the settings name and follows the OS while the mode is "system". High contrast is a scheme rather than a fourth mode because it needs a light and a dark version like any other. Pure black is meant for the dark mode of an OLED screen and has no light design of its own: by day it is the neutral palette, and its card in Settings says so. High contrast is held to AAA: text at 7:1 (WCAG 1.4.6), medium emphasis equal to high, solid field borders, stronger dividers and a 3px focus ring. What a palette sets beyond colour lives in its `variables`, which Vuetify writes out as `--v-*` custom properties on the theme class: `app-field-border-opacity` is read by `contrast.scss`, `app-focus-width` by `focus.scss`.

The base colours — background, surfaces, text, outlines, status colours — change only by scheme, never one by one (the user's decision, 2026-10-28): they stand in a dozen contrast pairs with each other, and a free choice of one breaks the others. The accent is the one colour a user picks, from ten swatches or with the system's own colour picker. It is stored as the colour the user chose, never as the colour drawn: `fitAccent` (`src/utils/accent.ts`) fits it into each palette, keeping its OKLCH hue and chroma and moving its lightness until it stands at the scheme's text ratio from the background, the surface, the surface variant and its own 12% tint — darker on a light palette, lighter on a dark one. A colour that already passes is kept as it is. So one accent becomes a colour per palette, and switching the mode or the scheme refits it instead of drawing an unreadable one. The background colour is the text on the accent, since it stands exactly as far from it. OKLCH rather than HSL because its lightness follows the eye, so moving it leaves the hue where it was. Deriving the whole palette from the picked colour, as Material 3's dynamic colour (`material-color-utilities`) does, was set aside: it would recolour the surfaces as well.

`src/plugins/__tests__/themeContrast.test.ts` holds every scheme to its level and every fitted accent — each swatch and a grid of 222 colours a user could pick by hand, in every scheme and mode — to the pairs the primary colour is drawn in. `e2e/a11y/axe.spec.ts` runs high contrast in both modes over every state with axe's AAA rules on, and the other schemes and three accents over six states.

Like the text size, the scheme and the accent are this device's own (the user's decision, 2026-10-28): a backup restore takes them (settings are not synced), and `parseSettings` defaults both when absent. They apply before the first paint: `vuetify.ts` builds the themes with the saved accent and starts on the saved scheme, and `useAppTheme` keeps them in step with every later write. It also writes the theme's background into `<meta name="theme-color">`, which `index.html` starts at the standard light background, so the browser bar and an installed app's status bar follow the theme. `buildThemes` hands Vuetify copies: Vuetify keeps a theme it has no default for by reference, and fitting an accent into its colours in place would otherwise change `SCHEMES` itself.

The pickers in Settings → General are native radios inside their labels, so the role, the arrow keys and the checked state are the browser's. Each radio is unseen but covers its card or circle, so a tap anywhere reaches it and a screen reader's highlight shows where it is. The chosen one carries a check, not colour alone, and the samples keep their colours in a forced-colours mode (`forced-color-adjust: none`). The custom colour is a row under the accent group rather than one more circle in it, named by its visible text: a radio group may hold only radios. It stays a native colour input, which NVDA with Chrome announces poorly on Tab; see [the audit's accepted limitations](accessibility-audit.md#accepted-limitation).

## Section colours

A dream, a goal and a group can pick a colour for the section it heads (`SectionColor` in `src/types/color.ts`: `color?`, `paintItems?`; the user's request, 2026-10-28). Without one the section is what it always was: an `outline` border and a legend in `on-surface-variant`. With one, the border and the legend take it; with "Colour the text inside" on as well, so do the rows inside — their names, notes and checkboxes, which inherit the row's colour. A row's date and its "Cancelled" set Vuetify's medium-emphasis colour on themselves and stay grey. The switch is disabled while no colour is picked, and `paintItems` is stored only as `true` and only beside a colour.

The colours are the accent's (the user's choice): the default grey, the ten `ACCENT_SWATCHES` and one picked by hand, in `ColorSwatches.vue`, the picker `AccentPicker` now wraps too. Like the accent, the colour is stored as picked and fitted at render time: `sectionColorFor` (`src/plugins/theme.ts`) moves it in OKLCH lightness alone until a note drawn in it — the faintest text, at the opacity `contrast.scss` gives a note on top of its row's colour — stands at the scheme's text ratio from the background and the surface, and an empty checkbox, at medium emphasis, at 3:1. `themeContrast.test.ts` holds every swatch and the 222 hand-picked colours to that in every scheme and mode, and axe checks the coloured sample data on the Goals page in every scheme. The list fits the colour where it draws it: `EntityListSection` reads the scheme and mode on screen through `useThemeOnScreen`, which reads Vuetify's theme rather than the settings store, so the presentational components need no palette handed down to them. The containers only pass the parent's stored colour through `ListSection`.

On screen today: a dream's colour on the Goals page, a goal's on the Tasks page. No list sections by group (see below), so a group's colour is stored and edited but shows only in its own dialog's read view, until a list sections by group (the user's decision, 2026-10-28). The matrix draws no sections and so no colours.

The fields raised `SYNC_SCHEMA` to 5: an older device would drop them and win the next merge without them. `BACKUP_VERSION` stays 4: both fields are optional, so every version 4 file still reads, and raising it would have refused the backups already made; an older build restoring a newer file loses only the colours.

## Dream/Goal/Group/Task pages & dialogs

`DreamsPage`, `GoalsPage` and `GroupsPage` are separate thin container sets rather than one generic "entity page," because Goals need grouping by parent Dream and Dreams don't — avoiding a component that branches internally on entity type. A goal's section label is its Dream's name regardless of the Dream's own status: a goal can outlive its Dream closing, and hiding the section then would lose information. Only **Cancel** cascades to children, never Done or Reopen — cancelling is an active decision to abandon a branch, while Done/Reopen says nothing about what should happen to relatives. That is why cascading lives in `useCascadeCancel`, which the Dreams and Goals containers call after the user confirms it, rather than inside the store's `close()`: the store closes exactly the record it is given. A parent picker (`dreamId`, `goalId`, `groupId`) never offers a closed record as a _new_ choice, but a record's already-assigned closed parent stays selectable, so editing something doesn't silently sever an existing link.

Whether toggling a record counts as "marking done" or "reopening" is derived from which tab the user is viewing (Active vs. History), not the record's current status — this encodes a specific prior bug fix, so don't reintroduce a status-based check here. `AddEntityDialog` is intentionally not built on top of `EntityDialog` (which is shaped for view/edit-toggle plus cancel-record, not a tab strip); each of its Dream/Goal/Task tabs keeps independent local field refs so switching tabs never discards another tab's in-progress input. Any `EntityDialog` opened in `mode="add"` shows no bottom action row or explicit Cancel button — dismissed only via backdrop or Escape, consistently across every type. An empty parent-picker selection is represented as `''` in the UI and normalized to `undefined` on save.

A group is a goal without a dream, a deadline or a note: a name and a colour, so `GroupsPage` is a flat list like `DreamsPage`. A task's group is independent of its goal (decided 2026-10-24) — the task dialogs carry a second picker, and the tasks page keeps sectioning by goal only: sectioning by both would show a task in two places, or make one link win over the other. The group a task sits in shows in the task dialog's read view instead, beside its goal. Cancelling a group cascades to its active tasks the way cancelling a goal does, whatever goal they also sit in. The Settings page gives groups the confirm switches but no rows toggle, since there is no note for a second row.

With four tabs, `AddEntityDialog` would overflow a phone: Vuetify gives each tab a 90px minimum, which scrolled the first tab out of view, so the tabs split the width by their own labels and scroll only at a large text size. Its tab bar is also kept from shrinking — the dialog's card is a flex column, and the task tab's form, taller than the screen at 150%, squeezed the bar to zero height. The bottom bar runs Dreams, Goals, Groups, the add button, Tasks, Matrix (the user's choice), so the add button sits off-centre; with five pages, the labels stop growing with the text size once they would spill into the next button. With some pages switched off, the add button stays between Dreams/Goals/Groups and Tasks/Matrix, so every page keeps its side (also the user's choice, 2026-10-24); only when nothing is left on its left does the first page on its right move over, giving Tasks, the add button, Matrix — or a page and the add button. With only Dreams, Goals or Groups shown, the add button closes the bar, and with none at all it stands alone. When one tab is left, the add dialog drops its tab bar.

## PWA / offline

The entire install-before-offline priority exists because Safari deletes all site data — IndexedDB, localStorage, the service worker registration — after 7 days without a visit; a PWA installed to the home screen (`display: standalone`) is exempt from that timer, making install the only way to actually trust storage on iPhone. Caching is precache-only, with no Workbox runtime-caching rules (no NetworkFirst/StaleWhileRevalidate) — deliberately not added "for later," since there's no backend and no network calls after initial load. `registerType: 'autoUpdate'` (silent service-worker takeover) is an accepted risk: if the app is open during a deploy, navigating to the lazy-loaded matrix chunk could hit a bundle that no longer exists; the documented fix if it ever happens is switching that route to a static import. `navigator.storage.persist()` is requested once at startup, and a refusal is never surfaced to the user, only logged in dev. Service workers require a secure context — `localhost`/`127.0.0.1` count, but a phone hitting `http://192.168.x.x` doesn't — so offline behavior on a phone can only be verified after deploy or through an HTTPS tunnel, never over plain LAN.

## Sync/WebRTC transport

Sync goes through the user's own [`workspace-server`](https://github.com/FLighter7/workspace-server) on the local network; it replaced the QR peer-to-peer sync on 2026-11-10. The contract is the server's `docs/protocol.md`; how the server works is its `docs/architecture.md`. The names below (`buildServerAnswer`, `ChannelFraming`, `ServerClient`, `SyncEngine`) are the package's, see "Where the code lives". The QR sync needed two code transfers for every sync, could not reach a computer behind a full-tunnel VPN (Chrome gathered its one host candidate on the tunnel), and did nothing on its own.

**No signaling.** The server is ICE-lite with a fixed ICE password and a long-lived certificate, both in the pairing code with its port and hosts. To connect, the device makes its offer and sets an answer it builds itself from that data (`buildServerAnswer`), choosing the server's ICE ufrag at random for each connection; the server recognises the connection by the first STUN binding request, which it verifies against its password. A throwaway Go + Pion spike on 2026-11-07 established the rest: WebKit connects to a `.local` candidate only when the name looks like a browser's own (`<uuid>.local`), libwebrtc prefers IPv6 when a name has both kinds of record (so the name carries A records only), the server's LAN IPs in the code make mDNS optional and get past a VPN, a connection opens in 150–200 ms, and one found dead on return from the background is replaced in about as long. iOS asked for no permission.

**The channel.** One data channel per connection, framed as the server's protocol says (`ChannelFraming`): JSON text frames with a `t`, and a body announced by `bytes` that follows as binary messages of at most 16 KiB — the size every browser has carried reliably, so the document has no size cap of its own. Sending pauses while more than 1 MiB waits in the channel's buffer and resumes at 256 KiB, since overfilling it closes the channel. `ServerClient` runs one request at a time and hands `changed` pushes to the engine.

**When it syncs** (`SyncEngine`): the connection is open only while the app is on screen. Becoming visible, a `changed` push, a local edit (3 s after the last one), `online` or Sync now each lead to a sync; hiding closes the connection and cancels every timer. A lost or refused connection retries after 2, 5, 15, 30 and 60 s, then every 5 minutes, while visible. So does a server-side failure (`internal`, which any error code this build does not know is read as), and a device whose address the server blocks (`blocked`, after 10 failed attempts from it in a minute, for 10 minutes) retries once a minute, since attempts during a block do not extend it; both keep the pairing and show as paused, not stopped, on the Sync page. A pairing refused as `blocked` consumes nothing, so while pairing the camera tries the same code again once a minute; any other refused code it ignores until the user pastes it. What retrying cannot cure — `tooLarge`, `notJson`, a conflict that kept recurring — waits for the next edit, push or Sync now, and what only a new pairing cures (`badToken`, `serverChanged`, `unknownApp`) stops sync and offers Pair again. The client's own habits keep it inside the server's other limits: it reads every reply before it sends the next request, so unread replies never pile up, and after pairing it sends `head` at once, the frame that confirms the pairing to the server; a session that ends before then leaves a stored token the server has deleted, and the next `hello` gets `badToken`. There is only ever one connection: a new one closes the previous `RTCPeerConnection` first, and anything still in flight on the old one stands down. A sync reads `head`, skips the rest when neither the server's etag nor the local change count moved, and otherwise reads the document, merges, replaces the local list if it changed and writes with the etag it read; a `conflict` re-reads and re-merges up to three times.

**The document** is a backup version 4 file without settings, plus `syncSchema`, so the file on the server's disk restores through Settings → Restore as it is. A document from a newer build is neither merged nor written — writing it back would drop fields this build does not know; one with an older or missing `syncSchema` is read normally and written back with this build's. One that does not parse is never written over: sync stops until it parses again, and the server's history keeps the previous versions. A device's first sync merges, it never replaces, so pairing a device that already holds data adds it to the server's list. A restore from a backup replaces only the local list, and the next sync merges it with the server's copy like any other list: a restore does not roll the server back.

**Decided by the user (2026-11-07).** A server on the user's own computer, not on the internet, and one that knows nothing of any app's data: it stores bytes, checks that they are JSON and tells versions apart by their SHA-256 (the etag), one document per app. One server serves several independent single-user apps; this one's id is `todo`. Pairing uses a one-time secret from the server's page (valid 10 minutes or one pairing), with no confirmation button on the server, and a server restart never needs pairing again. The channel stays open while the app is on screen and closes when it is hidden, on phones and desktops alike. Settings are not synced (see [Settings](#settings)). The QR sync was removed rather than kept beside the server.

**Passing a code on through a paired device (2026-11-12).** Pairing a laptop meant carrying it to the server's screen or sending the code to it through a messenger or email. Now a device that is already paired passes the code on: Sync → "Pair another device" (`PairingRelay`) reads the server's code with the camera or from a paste, checks it with `parsePairingCode` and shows it again as a large QR code (`QrCode`, drawn by `uqr` as an inline SVG, black on white in every theme), with Share where the browser shares text (AirDrop, Quick Share) and Copy (Universal Clipboard). The receiving device pairs as always, through its own scanner or paste field; the server and the protocol did not change. A device cannot simply push the code to an unpaired browser: that browser has no channel to anything until it has what the code carries (addresses, certificate fingerprint, ICE password), so the last hop is always its own camera, keyboard or clipboard. The relaying device never pairs with the code and never stores it: the code lives in the dialog's state and is gone when the dialog closes, since it holds a valid one-time secret for its ten minutes. A code for a server other than the device's own (`serverId`, which the `serverSync` store exposes from the pairing) is passed on with a notice naming that server. The e2e test decodes the QR code on screen with `qr-scanner` and pairs a second browser with what it read, against a real server.

**Through a subordinate when the main is away (2026-11-12).** The user's laptop can run its own workspace-server linked to the PC's as a **subordinate**: it keeps the main's documents on its disk, at home and away, and admits the main's devices by the token hashes the main sends it. Devices still pair only with the main; a subordinate refuses `pair` with `notMain`, which the Sync page explains ("this is a second server, linked to a main one…"). The design is the server's (`docs/architecture.md`, "Server modes and the link"); what this app sees:

- **The pairing learns the subordinates.** The main lists them in every `welcome`, and the package keeps them in the pairing record as `fallbacks` (optional: a record saved before reads as having none, so nobody paired again). Each `welcome` from the main replaces the list.
- **Which server.** With fallbacks known, the engine connects to the main and every subordinate at once, takes the main if it answers within 2 s of the start, and otherwise the subordinate that answered; a dead main holds its attempt until it times out (8 s), so nothing waits for it. It stays on that server until the app is hidden and shown again, which prefers the main again. Only the main's refusals stop sync: a subordinate that has not yet heard of a newly paired device (it learns at its next link with the main) refuses it with `badToken`, and the engine treats that server as away.
- **The merge did not change.** The token, the device id and `lastEtag` are shared by every server, since an etag is the document's hash. The server's copy still wins a tie, and the main's copy wins on the subordinate when both moved apart, the subordinate's own going to its history; this app then merges what it holds and writes back only what the server lacks, as against any server. So a change made through the laptop while the PC was off reaches the PC when the two meet, and one made at home while the laptop was away reaches the laptop.
- **What the Sync page shows.** "Server: {main}" stays, and while the connection goes through a subordinate a line under it names that one: "Through {name} while this server is out of reach" (`serverSync.via`, from the engine's `SyncState.via`). The screen reader hears it with the panel; the NVDA run is still to be done.
- **Limits.** Disconnecting while synced through the laptop forgets the pairing here, but the main keeps this device until it is removed on the main's page. A device removed on the main is still admitted by a subordinate that has not reached the main since. The package with fallback servers is not on npm yet: this app runs it through the committed `link:` until the user publishes it.
- **Tests.** The package's own unit tests cover the choice of server; `e2e/server-hub.spec.ts` runs a main and a laptop's server built from `../workspace-server`, linked over loopback: a browser paired with the main learns the laptop's server, syncs through it while the main is stopped, and both servers and both browsers converge, also after both servers moved while apart, with the laptop's own version found in its history. The laptop's own code is refused with its reason.

**Where the spike's devices stood.** Mac Chrome, iPhone Chrome and iPhone Safari, as a tab and installed to the Home Screen, all connected by IP and by `<uuid>.local`; Chrome carried 1 MB and the `changed` push, and came back from the background. Android and desktop Safari were not tested — the user judged them unimportant for now, Android Chrome sharing desktop Chrome's engine. A web app installed on iOS keeps its storage apart from Safari, so pairing has to happen inside the installed app.

**Changing addresses and being away.** The pairing and every `welcome` carry the server's `<uuid>.local` name and its current LAN IPs, and the device keeps the latest list, so a changed IP is reached through the name. Only when the name cannot be resolved (mDNS blocked on that network) and the IP changed too does the device lose the server; a DHCP reservation for the server's computer avoids that. Away from home the app works offline and, while on screen, keeps trying on the retry schedule — about a dozen attempts an hour, each a few UDP packets to private addresses and one mDNS query, carrying no data and no token (the token travels only inside the encrypted channel), and none while the app is closed.

**Where the code lives (decided by the user, 2026-11-10).** The transport and the engine moved out of this app into the npm package `@flighter7/workspace-client`, which workspace-server builds in its `client/` folder. Other apps will sync through the same server, and each would otherwise copy the most fragile code here. This app keeps its document (`syncDocument`), its merge (`planServerMerge`) and the adapter between them and the engine (`todoSyncAdapter`). A `DocumentError` from the adapter halts sync with this app's own codes (`newerSchema`, `badDocument`). The pairing key `todo.server`, the record's shape, the app id `todo` and every error code stayed as they were, so devices paired before the move did not pair again.

- **No Protobuf.** It was considered as a single source for the contract and turned down: every planned client is a TypeScript web app, and Protobuf generates only message types, not the SDP answer, the pairing code, chunking or the retry policy, where drift would actually hurt.
- **Vectors pin the contract.** Shared vectors in the server's `testdata/conformance/` are played by both the server's Go tests and the package's tests. The wire stayed at `proto` 1; the server had never been released.
- **Publishing is by hand.** The user publishes the package to npm; no workflow does. A change is checked here against a `link:` to the local package before it is published.
- **Licence and package manager.** The package is licensed CC BY-NC-ND 4.0. Both repositories moved to pnpm at the same time.

**Risks and open points.** WebKit's acceptance of UUID-shaped `.local` names is observed behaviour, not a documented contract; the IPs in the pairing are the fallback. Chrome's Local Network Access restrictions do not cover WebRTC today; if they ever do, a permission prompt may appear once. Several tabs of the app each hold their own session, which is harmless (writes are compare-and-swap) but duplicates traffic. A server whose data was reset gets a new certificate and `serverId`; the pinned fingerprint then fails the DTLS handshake, which the browser reports like any failed connection, so the Sync page says "Server not reachable" and keeps retrying, since nothing tells a reset server from one that is away: a STUN request with the old ICE password gets no answer at all. The page says so under that line — if the server's data was deleted or its port changed, disconnect and pair again with a new code — and Disconnect and a new code recover it. The header's Sync button shows no state; that was left open.

## Backup format

A backup is version 4: `{version, exportedAt, items, settings?}`, every item in one list. Versions 1–3 are refused rather than migrated, and so is a file that repeats an id, since every type shares one key space and the duplicate would silently collapse into one record. Restore fully parses and validates a backup file before touching storage at all, so a corrupt file can never destroy the existing list, and then writes it in one IndexedDB transaction. Import replaces the whole list rather than merging it — the original reasoning (no per-record timestamps existed yet) predates sync's `updated` field and is now stale, but no later spec revisited backup-import behavior, so replace-not-merge is still what the code does, just without its original justification.

## Accessibility

The target is WCAG 2.2 AA. The audit of 2026-10-27, its findings and the backlog it left are in [accessibility-audit.md](accessibility-audit.md); these are the conventions it settled.

- **A page change moves no focus.** The bottom bar behaves like a native tab bar: the focus stays on the link, the page is announced through the live region, and `document.title` and a visually hidden `h1` name it. Moving the focus to the heading was the alternative; it was rejected because the bar sits at the end of the document, and every page change would have sent a keyboard user back to the top to reach it again. Each route names its page in `meta.titleKey`.
- **One live region says what moves no focus.** `useAnnouncerStore().announce(text)` (`src/stores/announcer.ts`), rendered once by `DefaultLayout`, from the start: a region created together with its text, as Vuetify's snackbar creates its own, is often not announced. The snackbar's text is `aria-hidden` so its notices are not said twice. A container that closes, reopens, saves, cancels or adds a record announces it; a component cannot, since it has no store.
- **Every dialog has a name, a way out and gives the focus back.** Its title is an `h2` with an id that `VDialog` points at through `aria-labelledby`, or an `aria-label` where there is no visible title; a dialog without a Cancel action has a Close button, since Escape, the scrim and Back are hard to reach for a touch screen reader; and it calls `useReturnFocus(open)` (`src/composables/useKeepFocus.ts`). Vuetify returns the focus only to an activator-slot trigger, and every dialog here opens through `v-model`. When the dialog closed the record its trigger sat in, the focus goes to the row that took its place: a store write replaces `records` before it awaits storage, so the list has re-rendered by the next tick.
- **A list of records is a list.** `EntityList` wraps rows in `role="list"`, one per section and one per run of loose records. A row is a `listitem` with `tabindex="-1"`: its keyboard stops are the checkbox, named "Done: <name>", and the name, a real `<button>`. `VListItem` turns Enter on that button into a click that bubbles to the row, so the row still opens on a click anywhere. A row never becomes a button itself: a checkbox inside a button disappears for a screen reader.
- **`VList` only for real lists of options.** Inside a `VList` an item gets `tabindex="-2"` and is reached by arrow keys only, and the list claims `role="list"` over whatever it holds. Settings were wrapped in one and Export, Restore and Sample data could not be reached by Tab. Outside a `VList`, a clickable `VListItem` is a tab stop with no role; give it `role="button"`.
- **Icon buttons and checkboxes name their object, not only their action**: "Add a task to Schedule", "Skip: 7 November, 09:00", "Done: Buy milk". The same bare name four times in a row tells a screen reader user nothing.
- **Selected state is exposed by hand.** Vuetify sets no `aria-pressed` in a `VBtnToggle`, nor any state on a menu's chosen `VListItem`; segmented buttons get `:aria-pressed`, a menu's current item `aria-current="true"`.
- **The focus ring is `src/assets/styles/focus.scss`**, 2px in the primary colour on `:focus-visible` (3px in high contrast, from the palette's `app-focus-width`). Vuetify's own focus treatment is a tint at 1.3–2:1. Anything that clips its content (`overflow: hidden` on a list item's content box, a segmented control) needs the ring drawn inside or the clip lifted.
- **The palettes live in `src/plugins/theme.ts` and `src/plugins/__tests__/themeContrast.test.ts` holds them to WCAG**, AA or AAA as each scheme says, with every accent a user can pick. A new colour, emphasis level or opacity a control draws with goes into the palettes and into that test with the backgrounds it sits on. The field outline's opacity is a palette variable that `contrast.scss` reads.
- **Text wraps rather than ending in an ellipsis** where nothing else shows the rest: dialog titles, Settings actions, record names, a select's value. A row grows a line instead. A field's label cannot wrap, so a long instruction goes into a persistent hint under a short label.
- **A field's message area exists only while it has a message.** `hideDetails: 'auto'` is Vuetify's default for text fields, selects and textareas, since an empty area is still a `role="alert"` and NVDA said "alert" for each one as a dialog opened; `src/assets/styles/fields.scss` keeps the space it took. A required field says "(required)" as part of its label, and carries no `aria-required` besides: NVDA reads a label's whole text, `aria-hidden` parts included, and said "required" twice.
- **A reason shown to the user is never an `error.message`.** The services describe their failures in English for a developer and give each a `code`; `useErrorReason` (`src/composables/useErrorReason.ts`) translates the code, and an error without one gets a general reason while its message goes to the console. A new failure a service can report needs a code and a message in all three locales.
- **The audit's tooling stays.** `e2e/a11y/` runs with `pnpm run test:e2e`; a violation that has to stay goes into `e2e/a11y/allowlist.json` with the finding that tracks it. The NVDA scenarios (`pnpm run test:sr`) are local only: CI runs on Linux, and Guidepup drives the real keyboard. Two things learnt there: Guidepup reaches the page by clicking the middle of the body, which on most pages lands on a row, so the scenarios turn pointer events off for that moment; and it keeps only the first burst of speech after a key unless started with `capture: true`, which misses a dialog announced after its transition.

## Testing strategy

Component tests use `@vue/test-utils` over `@testing-library/vue` because Vuetify overlays (menus, dialogs, selects) teleport outside the component's own DOM subtree, which breaks role/label queries; `happy-dom` is opted into per file (`// @vitest-environment happy-dom`) rather than as a global environment. Playwright was chosen over Cypress specifically because simulating two devices pairing over WebRTC in one e2e test needs independent browser contexts, which Cypress's one-tab-per-spec model can't provide. Playwright's bundled Chromium is a separate binary from the system Chrome build with the broken Cache API (see `CLAUDE.md`'s Chrome trap), so e2e PWA/offline tests run against it directly rather than needing Edge. `openServerChannel.ts` deliberately has no unit test, as `SyncConnection.ts` before it had none — mocking `RTCPeerConnection` end-to-end was judged brittle and low-value; its real behaviour is exercised by `e2e/server-sync.spec.ts`, which builds and runs a real workspace-server, recorded here so it isn't later mistaken for a coverage gap. Everything above the channel is unit-tested against a fake channel or a fake server. The e2e test has to reach the server at the machine's LAN address, which the pairing code carries: Chrome does not pair its host candidate with a loopback address. CI builds the server from source with Go; a machine without Go points `WORKSPACE_SERVER_BIN` at a built binary. No coverage threshold is enforced in CI, and visual regression and contract tests are explicitly out of scope (no design team, no backend API). Test files were moved from co-location beside their subject into a per-directory `__tests__/` subfolder (e.g. `src/components/__tests__/`) to keep the physical location one level down while staying near the code under test, rather than a single root `tests/unit/` tree or an editor-only virtual-nesting trick.

## Foundational storage/UI choices

IndexedDB was chosen over the File System Access API because Safari supports neither `showSaveFilePicker` nor `showDirectoryPicker` on macOS or iOS, ruling out file-based storage given iPhone is a target device. `idb` was chosen over Dexie because the dataset is personal-scale and fits entirely in memory — Dexie's indexing and live-query strengths aren't needed. Icons use `vuetify/iconsets/mdi-svg` (SVG paths from `@mdi/js`) instead of the `@mdi/font` icon font, specifically to avoid the font's ~400KB weight for ~7000 unused icons; the `aliases` icon subset is still pulled in separately because Vuetify's own internals (checkboxes, sort arrows, pagination) depend on it.
