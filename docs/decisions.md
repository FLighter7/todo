# Decisions

Durable rationale and conventions carried forward from the build stages' design docs (`docs/superpowers/specs/`, now deleted — every stage they described has shipped). `.claude/CLAUDE.md` covers day-to-day conventions and the traps already paid for; this file is the _why_ behind choices that aren't obvious from reading the code alone. Read it before revisiting any of these areas.

## Data model rationale

`Status` is a numeric enum rather than a `const enum` — `isolatedModules` forbids the latter — and it also covers a dream being deliberately abandoned ("changed my mind"), not just fulfilled. A goal's fuzzy `deadline: {year?, month?, day?, season?}` follows validation rules that live in `utils/deadline.ts`, not the type: `day` requires `month`; `month`/`day` and `season` are mutually exclusive; an empty object is invalid; a missing `year` means "the nearest future occurrence" and is allowed to drift in meaning year to year, by design; season boundaries are meteorological, so winter deliberately spans the Dec–Feb year boundary.

`Task.schedule` is a miniature VEVENT. There's no stored `periodType` field — one-time vs. recurring is derived from `rrule` being absent or `COUNT=1`, specifically to avoid two fields encoding the same fact and drifting apart. Editing a recurring task's schedule mutates the same record rather than splitting the series (no iCalendar `THIS-AND-FUTURE`); past completions stay valid because they're keyed by occurrence date, and a single moved occurrence is expressed via `exdate`+`rdate` instead. `pruneCompletions` exists because a recurring task is always `Opened` and therefore never swept by the general `collectGarbage` rule — left unbounded, a daily task over 5 years accumulates ~1800 completion entries.

`IndexedDbRepository.getAll` skips invalid records and surfaces a count via `lastError` rather than failing outright — a single corrupt record shouldn't take the whole list down. The sync payload carries a schema version and refuses a mismatch outright (`src/services/sync/SyncConnection.ts:169`, "The other device runs a different version. Update it and retry."). Lists sort newest-first by `created`, and a group's position follows its newest child's `created` — adding a task lifts its parent goal's group to the top.

## Sync merge base rule

`CLAUDE.md`'s "`completions` merge per-occurrence" is the _exception_, not the rule. The base rule is whole-record last-write-wins by `updated`: a concurrent edit to two different fields on two devices loses the earlier edit entirely. Per-field conflict resolution was judged disproportionate for a manually-synced personal list. When `updated` matches to the millisecond on both sides, the tie-break is local-wins — arbitrary, but it has to be deterministic or two devices merging the same pair could diverge permanently.

## Recurrence / rrule gotchas

The `tzid`→wall-clock conversion in `nextOccurrence` needs **two** `Intl.DateTimeFormat` `formatToParts` passes to stay correct across a DST transition — verified against an anchored `America/New_York` 09:00 schedule read from a `Europe/Warsaw` host, which came out an hour off for a whole month without the second pass. A related trap: feeding that same machinery a value that's _already_ in the schedule's wall-clock domain re-triggers the instant→wall-clock conversion and silently reinterprets it against the device's own OS timezone. The fix was factoring a shared core that takes an already-converted comparison point; `nextOccurrence` is a thin wrapper over it, and `listOccurrences`/the last-occurrence check call the core directly.

An `rrule` that fits no UI preset (multiple `BYMONTHDAY`, `BYSETPOS`, etc.) parses to `undefined` and surfaces as a read-only "Custom" option — a safety net for foreign or hand-edited data, since this app's own editor is currently the only writer of `rrule`. "After N occurrences" floors at 2 in the UI because `isPeriodic()` treats `COUNT=1` as _not_ periodic — allowing 1 would let the form silently build a rule that behaves like a one-time task through a different control. An "until" date is converted to 23:59 wall-clock so the picked day is always fully included regardless of the schedule's own start time. The occurrence window shown in `TaskDialog` (5 past, 5 future) is a fixed constant, not a setting. `rdate` is honored when reading a schedule but nothing in the app authors one yet — only `exdate` is ever written, via the skip action.

## Completion-history invariants

An occurrence never carries both an `exdate` entry and a `completions` entry at once — each store action (`setOccurrenceDone`/`setOccurrenceSkipped`) clears the other side before writing its own. Un-marking a completion still _writes_ `{done: false, at: now}` rather than deleting the entry — deleting it would let a stale `done: true` from another device win after sync with nothing left to outrank it, the same tombstone logic as the "no `deleted` flag" rule applied to a single occurrence. The automatic Opened↔Done transition on a bounded series' last occurrence never touches a `Cancelled` task and fires with no confirmation, unlike the manual close/reopen flow gated by `confirmDone`/`confirmReopen` — it's a side effect of a deliberate occurrence action, not a standalone status change. Stray `completions`/`exdate` entries orphaned by an edited `rrule` aren't deleted immediately; they just stop appearing in `listOccurrences` and age out through the existing pruning window, the same "invisible now, removed later" shape as a closed record.

## Deadlines

`formatDeadline` builds its working `Date` from a fixed placeholder year (2000, a leap year) whenever `deadline.year` is unset, so a bare "Feb 29" doesn't throw; the placeholder never leaks into the displayed string because the `year` format option is omitted, not because the value is special-cased.

**`resolveDeadline()` — the `{from, to}` date-range resolution that sorting and overdue-detection would need — was specified but never built.** No later stage picked it up. Goals with a deadline currently have no sort-by-deadline or overdue indicator; don't assume one exists without checking.

## Cross-cutting store gotcha: patches with `undefined` overwrite

`createEntityStore.ts`'s `update()` spreads the patch over the existing record, so a patch key that's _present_ with value `undefined` really does overwrite the stored field — it isn't treated as "leave this alone." Any dialog that hand-maintains a subset of a record as its editable draft has to include every editable field in that subset, or saving from the dialog silently erases whatever it omitted. This bug hit `GoalList`/`deadline` and, independently, `TaskList`/`schedule` before being generically retired: `TaskDialog` now takes a full `record: Task | null` prop instead of a hand-picked `initial: Partial<TaskDraft>`. Follow the full-record-prop pattern for any future dialog rather than reintroducing a partial draft type.

## Settings

`src/plugins/vuetify.ts`, `src/i18n/index.ts`, and `src/router/index.ts` call `settingsService` directly instead of `useSettingsStore()`, because they resolve their startup values at module-evaluation time, before `createPinia()` has run. The settings Pinia store itself is built with `reactive()` + `toRefs()`, not a plain object spread — a spread was found elsewhere in this codebase to freeze reactivity. Settings writes to `localStorage` skip `toStorable()`/`toRaw()` entirely: `JSON.stringify` reads a reactive proxy fine, and the structured-clone-rejects-proxies trap is specific to `IndexedDB.put`, not `localStorage`. `ThemeMenu`/`LocaleMenu` deliberately stayed in the app bar rather than moving into the Settings page when their storage moved there — a setting with an existing fast, one-tap UI doesn't relocate just because its persistence layer changed.

## Dream/Goal/Task pages & dialogs

`DreamsPage` and `GoalsPage` are two separate thin container sets rather than one generic "entity page," because Goals need grouping by parent Dream and Dreams don't — avoiding a component that branches internally on entity type. A goal's group label is its Dream's name regardless of the Dream's own status: a goal can outlive its Dream closing, and hiding the grouping then would lose information. Only **Cancel** cascades to children, never Done or Reopen — cancelling is an active decision to abandon a branch, while Done/Reopen says nothing about what should happen to relatives. Cascade child-counting lives at the container level rather than inside the entity stores, keeping dreams/goals/tasks mutually independent and unit-testable in isolation. A parent picker (`dreamId`, `goalId`) never offers a closed record as a _new_ choice, but a record's already-assigned closed parent stays selectable, so editing something doesn't silently sever an existing link.

Whether toggling a record counts as "marking done" or "reopening" is derived from which tab the user is viewing (Active vs. History), not the record's current status — this encodes a specific prior bug fix, so don't reintroduce a status-based check here. `AddEntityDialog` is intentionally not built on top of `EntityDialog` (which is shaped for view/edit-toggle plus cancel-record, not a tab strip); each of its Dream/Goal/Task tabs keeps independent local field refs so switching tabs never discards another tab's in-progress input. Any `EntityDialog` opened in `mode="add"` shows no bottom action row or explicit Cancel button — dismissed only via backdrop or Escape, consistently across all three entities. An empty parent-picker selection is represented as `''` in the UI and normalized to `undefined` on save.

## PWA / offline

The entire install-before-offline priority exists because Safari deletes all site data — IndexedDB, localStorage, the service worker registration — after 7 days without a visit; a PWA installed to the home screen (`display: standalone`) is exempt from that timer, making install the only way to actually trust storage on iPhone. Caching is precache-only, with no Workbox runtime-caching rules (no NetworkFirst/StaleWhileRevalidate) — deliberately not added "for later," since there's no backend and no network calls after initial load. `registerType: 'autoUpdate'` (silent service-worker takeover) is an accepted risk: if the app is open during a deploy, navigating to the lazy-loaded matrix chunk could hit a bundle that no longer exists; the documented fix if it ever happens is switching that route to a static import. `navigator.storage.persist()` is requested once at startup, and a refusal is never surfaced to the user, only logged in dev. Service workers require a secure context — `localhost`/`127.0.0.1` count, but a phone hitting `http://192.168.x.x` doesn't — so offline behavior on a phone can only be verified after deploy or through an HTTPS tunnel, never over plain LAN.

## Sync/WebRTC transport

The SDP signaling payload is deliberately compacted: raw SDP is only ~586 bytes to begin with (single ICE candidate, no ICE servers), and generic deflate barely helps on such high-entropy data (~570 bytes) — extracting just 4 fields (ice-ufrag, ice-pwd, cert fingerprint, candidate address:port) and reconstructing the rest from a template gets it down to ~212 bytes, the difference between an 85×85 QR code (hard to scan) and a 53×53 one (scans instantly). The payload format is `<version><type><mode>.<data>`, where mode `c` (compact) is primary and `f` (full SDP, deflate+base64url) is the fallback if compact parsing fails; the leading version character lets an old app detect "this format is newer than I understand" instead of garbling it. Manual copy/paste of the signal string is an equal, first-class fallback to camera QR scanning — it's the primary way to pair a phone with a camera-less computer, not a degraded path.

## Backup format

Restore fully parses and validates a backup file before touching storage at all, so a corrupt file can never destroy the existing list. Import replaces the whole list rather than merging it — the original reasoning (no per-record timestamps existed yet) predates sync's `updated` field and is now stale, but no later spec revisited backup-import behavior, so replace-not-merge is still what the code does, just without its original justification.

## Testing strategy

Component tests use `@vue/test-utils` over `@testing-library/vue` because Vuetify overlays (menus, dialogs, selects) teleport outside the component's own DOM subtree, which breaks role/label queries; `happy-dom` is opted into per file (`// @vitest-environment happy-dom`) rather than as a global environment. Playwright was chosen over Cypress specifically because simulating two devices pairing over WebRTC in one e2e test needs independent browser contexts, which Cypress's one-tab-per-spec model can't provide. Playwright's bundled Chromium is a separate binary from the system Chrome build with the broken Cache API (see `CLAUDE.md`'s Chrome trap), so e2e PWA/offline tests run against it directly rather than needing Edge. `SyncConnection.ts` deliberately has no unit test — mocking `RTCPeerConnection` end-to-end was judged brittle and low-value; its real behavior is exercised only by the e2e WebRTC scenario, recorded here so it isn't later mistaken for a coverage gap. No coverage threshold is enforced in CI, and visual regression and contract tests are explicitly out of scope (no design team, no backend API). Test files were moved from co-location beside their subject into a per-directory `__tests__/` subfolder (e.g. `src/components/__tests__/`) to keep the physical location one level down while staying near the code under test, rather than a single root `tests/unit/` tree or an editor-only virtual-nesting trick.

## Foundational storage/UI choices

IndexedDB was chosen over the File System Access API because Safari supports neither `showSaveFilePicker` nor `showDirectoryPicker` on macOS or iOS, ruling out file-based storage given iPhone is a target device. `idb` was chosen over Dexie because the dataset is personal-scale and fits entirely in memory — Dexie's indexing and live-query strengths aren't needed. Icons use `vuetify/iconsets/mdi-svg` (SVG paths from `@mdi/js`) instead of the `@mdi/font` icon font, specifically to avoid the font's ~400KB weight for ~7000 unused icons; the `aliases` icon subset is still pulled in separately because Vuetify's own internals (checkboxes, sort arrows, pagination) depend on it.
