# Дизайн: модель данных для синхронизации (этап 5a)

Дата: 2026-08-06

## Контекст

Этап 5 — ручная синхронизация двух устройств по WebRTC с установкой соединения через QR-код. Он разбит надвое: этот документ описывает **5a** — фундамент, на котором стоит любой обмен данными. Транспорт, QR и интерфейс соединения — этап 5b, отдельный спек.

Причина разбиения в том, что транспорт рискован (сжатие SDP до размера, читаемого камерой, — нетривиальная задача), а слияние данных — нет: это чистая логика, покрываемая тестами целиком. Строить рискованное поверх непроверенного не стоит.

## Почему модель приходится менять

Двусторонний обмен обязан отвечать на два вопроса, на которые нынешняя модель ответить не может.

**Одна задача есть на обоих устройствах, но отличается — чья версия верна?** Без отметки о времени последнего изменения выбрать нельзя: `created` одинаков, а различия могли возникнуть где угодно.

**Задача удалена на одном устройстве — что увидит второе?** Сейчас удаление стирает запись физически. При слиянии её отсутствие неотличимо от «эта запись ещё не создавалась», поэтому вторая сторона добросовестно вернёт удалённое дело обратно. Без следа от удаления оно будет воскресать после каждой синхронизации.

Ровно эти два вопроса и закрывают два новых поля.

## Изменения в модели

```ts
export interface Todo {
	id: string;
	title: string;
	note?: string;
	created: string;
	/** ISO 8601 UTC; обновляется при каждом изменении записи. */
	updated: string;
	period: TodoPeriod;
	important: boolean;
	urgent: boolean;
	done: boolean;
	/** Надгробие: запись удалена, но след о ней хранится ради слияния. */
	deleted: boolean;
}
```

**Удаление становится мягким.** Действие `remove` больше не стирает запись, а ставит `deleted: true` и обновляет `updated`. Физически запись остаётся в хранилище.

Чтобы это не протекло в интерфейс, store разделяет два понятия: `records` — всё, что лежит в хранилище, включая надгробия; `items` — вычисляемый список видимых дел, то есть `records` без удалённых. Представления продолжают работать с `items` и о надгробиях не знают. Синхронизация будет работать с `records`, потому что ей надгробия как раз нужны.

Надгробия накапливаются и никогда не исчезают. Для личного списка это приемлемо: запись весит около сотни байт, и даже тысяча удалённых дел не создаёт проблемы. Осознанно оставлено на будущее — чистка старых надгробий имеет смысл только когда обе стороны гарантированно их увидели, а такой гарантии без учёта устройств нет.

## Миграция

Существующие записи не имеют новых полей. Версия базы IndexedDB поднимается с 1 до 2, и в обработчике обновления все записи дополняются: `updated` получает значение `created`, `deleted` становится `false`.

Значение `updated = created` выбрано намеренно: оно правдиво (запись с момента создания не менялась в известной нам истории) и не даёт ложного преимущества при первом слиянии, в отличие от подстановки текущего времени.

## Правило слияния

Функция чистая и не зависит ни от хранилища, ни от транспорта:

```ts
mergeTodos(local: Todo[], remote: Todo[]): Todo[]
```

Записи сопоставляются по `id`. Для каждого идентификатора берётся версия с более поздним `updated`. Надгробие ничем не выделяется — оно участвует в сравнении на общих основаниях, поэтому удаление побеждает правку, сделанную раньше, и проигрывает правке, сделанной позже. Записи, которые есть только на одной стороне, переносятся как есть.

При совпадении `updated` до миллисекунды побеждает локальная версия. Выбор произвольный, но он обязан быть детерминированным: иначе результат слияния зависел бы от того, какое устройство его выполняет, и списки разъехались бы навсегда.

Это правило («побеждает последняя запись») теряет одновременные правки разных полей одной задачи: если на одном устройстве изменили название, а на другом — срочность, уцелеет только более позднее изменение целиком. Полноценное разрешение конфликтов по полям потребовало бы хранить версию каждого поля, что несоразмерно личному списку дел, синхронизируемому вручную.

## Формат резервной копии

Версия файла поднимается до 2. Разбор принимает обе:

- **версия 2** — читается как есть;
- **версия 1** — дополняется теми же правилами, что и миграция базы (`updated = created`, `deleted = false`), поэтому старые копии остаются пригодными;
- **версия больше 2** — отвергается, как и раньше.

Экспорт включает надгробия. Копия должна восстанавливать состояние целиком, а без надгробий восстановление из файла воскресило бы всё когда-либо удалённое.

## Проверка

1. Юнит-тесты слияния: обе стороны пусты; запись только слева; только справа; расхождение с более поздней левой; более поздней правой; равные метки; надгробие новее правки; правка новее надгробия; надгробия с обеих сторон.
2. Юнит-тесты store: `remove` ставит флаг вместо стирания; `items` скрывает удалённые; `records` их сохраняет; каждое изменяющее действие двигает `updated`.
3. Юнит-тесты формата: файл версии 1 читается и дополняется; версии 2 читается как есть.
4. В браузере: база, созданная старой версией приложения, открывается новой без потери дел, а у записей появляются новые поля.

## Вне области

Транспорт WebRTC, QR-коды, интерфейс соединения устройств, чистка старых надгробий, разрешение конфликтов по отдельным полям, учёт устройств.
