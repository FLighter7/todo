# Дизайн: экспорт и импорт резервной копии

Дата: 2026-08-06

## Контекст

Данные живут только в IndexedDB одного браузера. Синхронизации между устройствами ещё нет, а до неё — этап 5 с WebRTC — работы много. Всё это время единственная защита от потери списка — установленное приложение и надежда на браузер.

Резервная копия в файл закрывает разрыв: она маленькая по объёму работы, работает во всех браузерах и не зависит ни от сети, ни от второго устройства. Кроме того, она даёт способ вручную перенести дела между устройствами до появления синхронизации.

## Формат файла

JSON с оболочкой, а не голый массив:

```json
{
	"version": 1,
	"exportedAt": "2026-08-06T09:00:00.000Z",
	"todos": [{ "id": "…", "title": "…" }]
}
```

Оболочка нужна из-за одного известного факта: **модель данных будет переписана на этапе 6** — появятся горизонты, цели, частота повторения. Без поля `version` приложение будущей версии не сможет отличить старый файл от нового и либо молча испортит данные, либо откажет без объяснения. С версией оно сможет либо преобразовать старый файл, либо честно сказать, что формат новее поддерживаемого.

Поле `exportedAt` служит человеку: по нему видно, насколько копия свежая, ещё до импорта.

Имя файла — `todo-backup-ГГГГ-ММ-ДД.json`. Дата в имени, чтобы несколько копий в папке загрузок не перетирали друг друга и сортировались по порядку.

## Поведение импорта: замена, а не слияние

Импорт **заменяет** весь список содержимым файла.

Слияние выглядит заманчивее, но у него нет однозначного ответа на главный вопрос: что делать с делом, которое есть в файле и есть в приложении, но отличается? Правильно ответить на это можно, только когда у записей появятся метки времени изменения — а их нет и не будет до этапа 6. Придумывать половинчатое правило сейчас означает получить тихую потерю правок. Слияние — задача этапа 5, где оно и решается по-настоящему.

Раз импорт разрушителен, он требует подтверждения. Диалог показывает, сколько дел в файле и сколько будет потеряно, и когда файл был создан. Кнопка подтверждения названа действием («Заменить»), а не «ОК».

## Валидация: сначала проверить, потом стирать

Ключевое требование: **испорченный файл не должен уничтожить существующий список.** Поэтому порядок строгий — сначала разбор и полная проверка содержимого, и только если она прошла целиком, приложение трогает хранилище.

Проверяется: файл разбирается как JSON; это объект; `version` — число и оно не больше поддерживаемого; `todos` — массив; каждая запись содержит `id`, `title`, `created`, `period`, `important`, `urgent`, `done` нужных типов, а `period` — одно из двух допустимых значений. Любое нарушение прекращает импорт с сообщением, а список остаётся нетронутым.

Неподдерживаемая версия сообщается отдельным текстом: это не «битый файл», а «файл новее приложения», и пользователю полезно понимать разницу.

## Архитектура

Разбор и сборка формата отделены от работы с файлами браузера — так проверяемая часть тестируется в окружении `node`, без DOM.

```
src/services/backup/
	format.ts       — createBackup, parseBackup, BackupFormatError, BACKUP_VERSION
	format.test.ts  — тесты разбора и валидации
	file.ts         — downloadBackup, readTextFile: тонкая обёртка над Blob и FileReader
src/components/
	BackupMenu.vue  — пункты меню в шапке, диалог подтверждения
```

`format.ts` не знает ни о `Blob`, ни о `File`, ни о хранилище — только строка на входе и структура на выходе. `file.ts` не содержит логики и потому не тестируется.

Store получает действие `replaceAll(todos)`. Оно очищает хранилище и записывает новый набор, поэтому интерфейс `TodoStorage` расширяется методом `clear()`. Расширение осознанное: без него замена выглядела бы как перебор удалений по одному, что и медленнее, и не атомарно по смыслу.

## Проверка

1. Юнит-тесты `format.ts`: корректный файл разбирается; мусор, не-JSON, отсутствующие и неверно типизированные поля, недопустимый `period`, слишком новая версия — все отклоняются.
2. Юнит-тесты store: `replaceAll` заменяет содержимое и в памяти, и в хранилище.
3. В браузере: экспорт скачивает файл с ожидаемым содержимым; импорт этого файла после удаления всех дел восстанавливает список; импорт испорченного файла показывает ошибку и **не** трогает существующие дела.

## Что выяснилось при реализации

**Реактивные объекты Vue нельзя отдавать в IndexedDB.** Первая версия `replaceAll` перебирала `items.value` уже после присваивания и передавала в хранилище прокси, а не обычные объекты. Структурное клонирование в IndexedDB на этом падает, и восстановленные дела исчезали после перезагрузки — при том что на экране всё выглядело правильно. Юнит-тест это пропустил: реализация хранилища в памяти прокси принимает молча. Лечится тем, что копии готовятся до присваивания и записываются именно они.

Вывод шире одного метода: тесты store поверх in-memory не проверяют совместимость с IndexedDB, поэтому любое новое действие, которое пишет данные, надо хотя бы раз прогнать в браузере.

**Формулировки с числами обходятся без согласования.** Вместо «2 дел» и «task(s)» тексты построены как «Дел в файле: 2». Заводить правила множественного числа vue-i18n ради двух строк, из которых одна на русском требует трёх форм, — несоразмерно.

## Вне области

Слияние с существующими делами, автоматические копии, копии в облако, шифрование, выбор подмножества дел для экспорта.
